::: tip 摘要
一次 `parallelStream()` + `Apache HttpClient` 调用远程接口的排查记录：表象是大量 `Read timed out` 和 `429`，真正的关键不在“并发数多大”，而在 **8 秒读超时 + 服务端响应慢** 共同制造的高频重压。
:::

## 一、问题背景

### 1. 业务场景

项目为 `Spring Boot 1.5.22 + JDK 8` 的 Maven 工程。简单介绍背景：

1. 查询数据库，得到一批待处理数据（约 286 条）。
2. 对每条数据通过 `Apache HttpClient` 调用远端的接口，拿到对应数据做后续处理。

最初实现时，使用了 Java 并行流。

::: warning I/O 任务不适合用并行流
我当时没意识到 I/O 密集任务交给 `parallelStream()` 并不合适，算是踩坑的开始 ~~/(ㄒoㄒ)/~~。
:::

::: code-group

```java [旧实现 · parallelStream]
Map<String, String> zxTimeMap = dataList.parallelStream()
        .map(info -> {
            String response = HttpClientUtil.doPost(CODE_UNION_QUERY_URL, requestBody, headers);
            // 解析 response，返回 TID 与装箱时间的键值对
        })
        .filter(Objects::nonNull)
        .collect(Collectors.toMap(
                Map.Entry::getKey,
                Map.Entry::getValue,
                (v1, v2) -> v1
        ));
```

:::

HTTP 请求统一由 `HttpClientUtil.doPost(...)` 发送。

### 2. 问题现象

运行后控制台出现大量异常堆栈，主要表现为：

- 大量 `java.net.SocketTimeoutException: Read timed out`。
- 部分请求返回 `429`，响应体为 `{"code":429,"msg":"请求过于频繁，请稍候再试","data":null}`。
- 少量请求返回空结果。
- 最终只有 2 条数据拿到了装箱时间。

::: danger 核心矛盾
不是“一次发出 286 个请求”，而是“少量请求持续高频重压”，最终把上游服务压到限流。
:::

### 3. 原始日志时间线

从异常记录中还原出的关键时间线如下：

| 时间 | 事件 |
| --- | --- |
| 14:20:56 | 查询到待处理数据 286 条，开始并行处理 |
| 14:21:05 | 出现第一批 `Read timed out` |
| 14:21:05 ~ 14:22:13 | 持续出现 read timeout，累计 174 个 |
| 14:22:06 ~ 14:22:13 | 服务端集中返回 100 个 `429 请求过于频繁` |

## 二、代码分析

### 1. HttpClientUtil 的实现

`HttpClientUtil` 中每次发送请求时，都是 **新建一个 HttpClient，且 `HttpClients.createDefault()` 使用默认配置，用完立即关闭**。

::: note 为什么没改它
这是公司代码里已经封装好的接口。作为实习生，我不太想去动公司的历史代码（其实也怕影响别的地方），所以选择先排查原因。
:::

::: code-group

```java [sendHttpPost]
public static String sendHttpPost(HttpPost httpPost, int timeoutMs) {
    CloseableHttpClient httpClient = null;
    CloseableHttpResponse response = null;
    try {
        httpClient = HttpClients.createDefault();
        httpPost.setConfig(buildRequestConfig(timeoutMs));
        response = httpClient.execute(httpPost);
        // ...
    } catch (Exception e) {
        e.printStackTrace();
    } finally {
        if (response != null) {
            response.close();
        }
        if (httpClient != null) {
            httpClient.close();
        }
    }
    return responseContent;
}
```

:::

默认超时配置为 8 秒：

```java{1,3-7}
private static final int DEFAULT_TIMEOUT_MS = 8000;

private static RequestConfig buildRequestConfig(int timeoutMs) {
    return RequestConfig.custom()
            .setSocketTimeout(timeoutMs)
            .setConnectTimeout(timeoutMs)
            .setConnectionRequestTimeout(timeoutMs)
            .build();
}
```

关键点：我调用这个未显式传超时时间的 `doPost` 重载接口，实际走的就是默认 8 秒配置的 `HttpClient`：

```java{3}
public static String doPost(String httpUrl, Map<String, Object> maps, Map<String, String> headers) {
    return doPost(httpUrl, maps, DEFAULT_TIMEOUT_MS, headers);
}
```

因此，最初 service 中调用：

```java{1}
HttpClientUtil.doPost(CODE_UNION_QUERY_URL, requestBody, headers);
```

实际生效的超时时间就是 **8 秒**。

### 2. 异常被吞掉的问题

`sendHttpPost` 的 `catch` 里只有 `e.printStackTrace()`，然后返回 `null`。所以异常并没有继续向上抛给 service，service 层最终只是拿到一个 `null`，打印日志“查询装箱时间响应为空”。

::: info 为什么控制台看着像“异常没被捕获”
这些堆栈其实是 `printStackTrace` 输出到标准错误流，和带时间戳的正常日志交错在一起，肉眼看起来就像异常凭空出现、没有被捕获一样。
:::

### 3. 关键堆栈定位

`Read timed out` 的堆栈核心链路是：

```text
java.net.SocketTimeoutException: Read timed out
    at java.net.SocketInputStream.socketRead0(Native Method)
    at java.net.SocketInputStream.socketRead(SocketInputStream.java:116)
    ...
    at org.apache.http.impl.io.SessionInputBufferImpl.readLine(...)
    at org.apache.http.impl.conn.DefaultHttpResponseParser.parseHead(...)
    ...
    at org.apache.http.impl.client.CloseableHttpClient.execute(...)
    at com.hcf.smt.wc.web.utils.HttpClientUtil.sendHttpPost(HttpClientUtil.java:152)
    at com.hcf.smt.wc.web.utils.HttpClientUtil.doPost(HttpClientUtil.java:127)
    at com.hcf.smt.wc.web.utils.HttpClientUtil.doPost(HttpClientUtil.java:106)
    at ...TobaccoDataHandleServiceImpl.lambda$handleTobaccoZXTime$0(...:78)
```

堆栈停在 `DefaultHttpResponseParser.parseHead`，说明：

- TCP 连接已经建立成功，请求也已经发出。
- 客户端在等待读取 HTTP 响应头时，8 秒内没有读到数据。
- 这不是 `ConnectTimeoutException`，也不是连接池等待超时，而是 **读响应超时**。

### 4. 并行流的并发度问题

`parallelStream()` 默认使用 `ForkJoinPool.commonPool()` 线程池。

在 JDK 8 中，公共 `ForkJoinPool` 的默认并行度为：

```text
可用 CPU 核数 - 1
```

我的设备 CPU 有 20 个逻辑核，因此约 19 个 worker 线程。
不会一次性发送 286 个请求，而是排队处理：每个 worker 完成一条，再取一条。任何时刻并行请求大约只有 19 个。

### 5. 服务端负载情况推测

日志中统计到：

| 结果 | 数量 |
| --- | ---: |
| `Read timed out` | 174 个 |
| `429 请求过于频繁` | 100 个 |
| `result 为空` | 10 个 |
| 成功拿到装箱时间 | 2 个 |

174 个读超时，按 8 秒一个、19 个线程计算：

```text
174 × 8 秒 ÷ 19 个线程 ≈ 73 秒
```

这与日志里从开始到结束约 77 秒基本吻合。

::: tip 结论
当时并不是“286 个请求瞬间把服务端打爆”，而是“约 19 个并发、持续约 1 分钟的高频重压”。
:::

### 6. 被排除的错误结论

我根据平时自己开发的经验，先排查了两个方向，结果都没解决问题。

::: details 被排除方向一：HttpClient 默认连接池太小
虽然 Apache HttpClient 4.5.x 默认最大线程数 `maxTotal=20`、相同 ip:port 的并发请求数 `defaultMaxPerRoute=2`，但这里的 `HttpClientUtil` 每次请求都新建 HttpClient，各线程之间并没有共享连接池。

这也是我调试了半天、翻了公司源码才发现的，忍不住吐槽一句 ~~公司真是草台班子啊~~~。
:::

::: details 被排除方向二：286 个请求同时并发
`parallelStream()` 实际在途只有约 19 个请求，并没有把 286 个请求一次性打出去。

我甚至干过手动修改 `ForkJoinPool.commonPool()` 线程池线程数的事，23333。
:::

结果就是都没解决问题，之后通过 `Codex + DeepSeek V4 Pro` 模型才找到问题所在。

---

## 三、结果确定

### 1. 直接原因

最初版本的 HTTP 读超时只有 8 秒。服务端响应慢时，客户端在读取响应头阶段等满 8 秒，就抛出：

```text
java.net.SocketTimeoutException: Read timed out
```

### 2. 根本原因

上游服务 `10.154.80.209:8082` 在当前负载下响应慢，甚至出现限流。

客户端 8 秒超时又制造了“放弃请求 → 线程立刻取下一个数据 → 再发新请求”的节奏。服务端一边处理旧的慢请求，一边又收到新的请求，压力不断累积，最终触发 `429`。

::: danger 一句话总结
短超时 + 慢服务，会把客户端的请求节奏拉高，进一步加剧服务端压力。
:::

### 3. 为什么换成 CompletableFuture 后不报错了

我把并行流改成了自定义线程池（线程数是 19）+ `CompletableFuture`，同时把请求超时从 8 秒改成了 100 秒：

::: code-group

```java [调整超时时间]
String response = HttpClientUtil.doPost(CODE_UNION_QUERY_URL, requestBody, 100000, headers);
```

:::

表面上并发数仍然约 19，但客户端行为变了：

- 不再每 8 秒就放弃一个请求。
- 服务端慢，客户端就等待它真正返回。
- QPS 由服务端真实响应速度决定，而不是由客户端的并行流决定。

因此不会出现 `429` 和 `Read timed out`。

::: note 结论的边界
上述只是根据我的调试结果做的推测。作为实习生，我没有再去服务端核对对应时间段的服务端日志和限流配置，只在代码里留了注释，让后人能知道有这个问题存在。
:::

## 四、复盘

- [x] 定位 `Read timed out` 的直接原因：8 秒读超时。
- [x] 定位根本原因：上游响应慢 + 客户端超时制造的请求节奏放大。
- [x] 排除“连接池太小”和“286 个同时并发”两个误判。
- [ ] 后续可到服务端核对限流配置与对应时间段日志，进一步验证结论。
